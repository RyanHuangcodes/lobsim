# DECISIONS

One line per decision, with the reason. Section numbers refer to `SPEC.md`.

## Tooling and build
- D-001 CMake comes from a project-local `.venv` (`uv pip install cmake`), not a system install: the machine had no CMake, and a local venv changes nothing outside the repo. The same venv holds pandas + matplotlib for `tools/plot.py`.
- D-002 `CMakePresets.json` defines `debug`, `release` and `sanitize` (build dirs `build/<name>`): one short, identical command per configuration for every contributor and helper.
- D-005 The presets file uses `"version": 3`, which needs CMake 3.21+: version 2 makes `generator` mandatory and we pin none. On exactly CMake 3.20 the project still builds with plain `cmake -S . -B <dir> -DCMAKE_BUILD_TYPE=...`.
- D-003 Sanitize = Debug + `-fsanitize=address,undefined -fno-sanitize-recover=undefined -fno-omit-frame-pointer`, applied globally so the dependencies are instrumented too: UBSan findings must fail the test run, not just print, and stack traces must be readable.
- D-004 `BENCHMARK_ENABLE_WERROR OFF` and third-party targets treated as SYSTEM: "zero warnings" applies to our code; a newer compiler must not break a pinned dependency.
- D-006 `LOBSIM_WERROR` (default ON) adds `-Werror` to our own targets: "zero warnings" (Section 8) is then enforced by every build instead of by reading logs.
- D-007 With no `CMAKE_BUILD_TYPE` the build defaults to Release: a bare `cmake -S . -B build` should give the fast binaries the benchmarks describe.

## Matching engine API (Section 3 is silent on exact signatures)
- D-010 Both books expose the same non-virtual member API (`submit`, `cancel`, `modify`, `best_bid`, `best_ask`, `best_level`, `depth`, `order`, `resting_orders`, `validate`) and tests are written once as typed tests over both: a virtual base would add an indirect call to the hot path for no benefit.
- D-011 `Event` is a `std::variant<Ack, Reject, Trade, Cancelled, Modified>` appended to a caller-owned `std::vector<Event>`: trivially copyable alternatives, no allocation once the buffer has grown (Section 3.7).
- D-012 `Request` is a `std::variant<NewOrder, Cancel, Modify>` with a free `apply(book, request, out)`: fuzz, replay, bench and the exchange all feed the same stream type.
- D-013 `best_level(side)` returns the best `(price, total_qty)` without allocating: the exchange needs BBO quantities after every message and `depth()` returns a vector.
- D-014 `validate()` throws `std::logic_error` naming the first broken invariant; Debug builds call it inside the book after every message: a thrown error is testable and gives a message, an `assert` does neither.
- D-015 Event hash encoding: one tag byte (Ack 0, Reject 1, Trade 2, Cancelled 3, Modified 4), then every field in declaration order, 64-bit fields as 8 bytes LE, 32-bit as 4 bytes LE, enums and bools as 1 byte: fixed and platform-independent (Section 3.7).

## Matching semantics (cases Section 3 leaves open)
- D-020 `UnknownOrder` means "not resting right now": never-assigned, fully filled and already-cancelled ids are indistinguishable to the caller, and the id index only knows resting orders.
- D-021 Cancel reason for a market order: `SelfTrade` if STP `CancelTaking` stopped it (even with zero fills), else `NoLiquidity` if nothing filled, else `IOCRemainder`. A limit IOC remainder is always `IOCRemainder`, also with zero fills: Section 3.3.3 reserves `NoLiquidity` for market orders.
- D-022 A market order whose only opposite liquidity was its own orders cancelled under `CancelResting` ends with `NoLiquidity`: nothing filled.
- D-023 Post-only "would cross" is a pure price test against the opposite best, whoever owns it: Section 3.3.5 defines it by price only.
- D-024 A modify that loses priority re-enters as a GTC taker using the order's stored `stp` and `post_only`; under `CancelTaking` a self-match on re-entry cancels the re-entering order's remainder with `Cancelled(SelfTrade)`: Section 3.3.6 says it re-enters "as a new arrival".
- D-025 Same price with a larger qty moves the order to the tail of its own level (`priority_kept = false`); it cannot match because the book is never crossed.
- D-026 `Modified.new_qty` is the requested new remaining quantity, before any matching the re-entry causes: the event is emitted first (Section 3.3.6).
- D-027 The modify `PostOnlyWouldCross` check applies only to post-only orders; a normal order modified to a crossing price trades as a taker.
- D-028 `Cancelled.qty_cancelled` is the order's remaining quantity at that moment; `Trade.aggressor_side` is the taker's side.
- D-029 FOK is valid only on limit orders (a market order must be IOC, Section 3.2), and a FOK that passes the dry run always fills completely, because execution walks the same orders the dry run counted.
- D-030 A market, limit IOC or limit GTC taker stopped by `CancelTaking` gets `Cancelled(SelfTrade)` for its remainder: Section 3.4 states it without exception, so D-021's "limit IOC remainder is always IOCRemainder" applies only when STP did not stop it. (A FOK can never end this way: it either fails the dry run or fills before reaching its own order, D-029.)

## OrderBook internals and the differential fuzz test (Phase 3; Section 3.5 is silent on these)
- D-040 `ObjectPool` keeps its free list in a separate `std::vector<void*>`, not as links inside free slots, and reserves that vector to the pool's full capacity whenever a chunk is added: a released slot is ASan-poisoned and must never be read, and `destroy()` then never allocates.
- D-041 The pool hands out the most recently released slot first (LIFO) and uses chunks of 4096 slots: the reused slot is still in cache, and one chunk of 64-byte orders (256 KiB) covers a typical book without growing.
- D-042 `ObjectPool<T>` requires a trivially destructible `T` (static_assert): the pool does not track which slots are live, so it cannot run destructors when it dies; `Order` is trivially destructible.
- D-043 A modify that loses priority returns the old `Order` node to the pool and takes a fresh one if the remainder rests (same `OrderId`, same index slot): one removal path for cancel, fill and modify, and no node that is both resting and the taker during a match.
- D-044 The id index grows (geometrically) only when an order rests; lookups bounds-check, so any id beyond it is `UnknownOrder`. `validate()` checks every resting order's own slot and compares `indexed_`, the number of non-null slots kept by the index's single writer `set_index()`, with the number of resting orders, instead of scanning the whole index: the index grows with every id ever rested, which would make a per-message `validate()` O(total ids). It also checks pool live count == resting orders (catches a leaked node).
- D-045 `OrderBook` is neither copyable nor movable: orders point at map nodes and pool slots, so a copied book would alias the original's orders.
- D-046 `ReferenceBook::validate()` finds duplicate ids by sorting a copy (O(n log n)) instead of comparing every pair: same check, fast enough to run twice per fuzz message.
- D-047 The fuzz generator uses SplitMix64 (`tests/support/splitmix64.hpp`) with rejection-sampled ranges, and never draws two random values inside one function-call argument list (unspecified evaluation order): the same seed gives the same stream on any compiler.
- D-048 `ConservationChecker::check_fast()` gives `check()`'s verdict in O(open + touched) per message by comparing the book's `resting_orders()` with the model's live count instead of re-querying every finished id. The fuzz test runs it on every message; on every 20th seed `check()` runs beside it and the verdicts must agree; `--long` uses `check_fast()` only, since `check()` is quadratic over 10^6 messages.
- D-049 The default fuzz mode is registered as 10 ctest entries of 20 seeds each, and the test presets run 10 jobs: the sanitize build takes several minutes serially.
- D-050 Adding an order to an existing price level costs one `std::map` lookup, O(log L), not the O(1) of Section 3.5's target: 3.5 also fixes the level container as `std::map`, which has no O(1) lookup by price, and an incoming order carries no pointer to its level. Only the best level is O(1) (`begin()`). L is tens of levels in the simulator, so this is a handful of comparisons; an O(1) price index is the array-ladder stretch goal of Section 10.
- D-051 `tests/unit/order_book_validate_test.cpp` also holds a deep-book differential test (8,500 resting orders, three pool chunks, scattered cancels, slot reuse, full drain) with an independent scan of the whole id index: the fuzz test keeps the book under about 500 orders, so it never leaves the first pool chunk.

## Benchmarks (Phase 4)
- D-060 The benchmark stream measures order lifetimes in new-order arrivals (exponential, mean 1,500), not in time: the bench has no clock, and this holds the book near 1,000 resting orders like the simulator's noise flow.
- D-061 `lobsim_bench` makes three passes over the same stream: timed per block of 4,096 messages (throughput), per batch of 32 (body of the distribution) and per message (far tail and maximum). On the benchmark machine the clock advances in 41 ns steps and a message takes about 21 ns, so single-message samples cannot resolve the body (Section 7: "time batches if it's significant").
- D-062 The allocation counter is on only while engine calls run, and the caller's event buffer is reserved once: every counted allocation is then the engine's own.
- D-063 Each microbenchmark times a batch of 128 operations and undoes it outside the timed region: pausing the timer per operation costs more than the operation, and the book must stay near its nominal size.
- D-064 The harness fails (non-zero exit) if its passes disagree on the event count, if an order id differs from the predicted one, or if `OrderBook` and `ReferenceBook` hashes differ on the shared prefix: a benchmark of a broken run is worse than none. The passes are compared on event counts, not on a full event hash: hashing inside the block-timed loop would add its own cost to the time being measured. The full hash is computed in the per-message pass, outside its timer pairs, and that is the one compared with `ReferenceBook`.
- D-065 `micro_bench` has two calibration benchmarks that run an empty operation in batches of 128, with and without one timer pause per batch: the difference is the timer overhead included in the per-operation times of the five benchmarks that pause, and the README reports it instead of an estimate.

## Simulator core (Phase 5)
- D-070 Every tie in the simulator is broken by one rule: the global `seq` of the event queue (events with equal time run in scheduling order); event kind and agent id never take part. Agents are created noise traders first, then the informed trader, then the market maker, so agent order fixes the `seq` of everything scheduled in `on_start`.
- D-071 Each random consumer has its own stream, seeded from `(master seed, role, index within role, purpose)`, never from the global agent index: adding a noise trader, the informed trader or the market maker leaves every other stream unchanged (tested by comparing the `NewOrder` lines of N and N+1 traders).
- D-072 `ctx.rng()` is drawn only in `on_start` and `on_wakeup`. A draw triggered by a message uses a separate stream owned by the agent: the noise trader draws each order lifetime, on the `Ack` of a limit order, from its own lifetime stream (purpose 2). Reason: whether a reply is handled before or after the agent's next wakeup depends on latency jitter, which is consumed at a rate set by every other agent; sharing the decision stream would re-phase it when an agent is added.
- D-073 One `schedule_wakeup` is one `TimerQueue` entry and each `on_wakeup` pops exactly one (`pop_due` throws if none is due): a lost or duplicate wakeup is an error, and timers add no second tie rule. Timers are never erased; an obsolete cancel timer is popped and ignored.
- D-074 `orders.log` is plain text with decimal integers only, written and read through one codec (`format_request`/`parse_request`, `format_header`/`parse_header`); enums and bools are their integer values. The replay tool of Phase 7 and the replay test use the same functions, and the test replays the parsed text, not retained `Request` objects.
- D-075 `lobsim_run` has an extra `--duration-s X` override. If the shorter run is shorter than the configured warm-up, the warm-up is set to 0 (a short run has no warm-up to keep) instead of failing validation.
- D-076 Unknown keys in the config file are errors, as are missing keys and wrong types: a typo must not be silently ignored. `informed` and `mm` are optional sections; they are parsed and validated if present, but Phase 5 creates no agent for them, so runs with and without them are identical.
- D-077 A config duration that does not fit in 63 bits of nanoseconds (or is not finite) is an error naming the field: `std::llround` of such a value is undefined behaviour.
- D-078 `-ffp-contract=off` is PUBLIC on the `sim` target: the generators and the fundamental step are inline in headers and are compiled into every user of them, so the flag must reach them too; fused multiply-adds would make floating-point results depend on the build type.
- D-079 `Simulator::add_agent(agent, latency, role, index)` lets tests add scripted agents after the configured ones; they take their streams from `StreamRole::Test` (or any role and index the test gives) and are indexed after the configured agents.
- D-080 The exchange throws `std::logic_error` if the book is ever crossed after a request, in every build type: it can only mean an engine bug.
- D-081 Each agent has one latency generator shared by its three channels (entry, response, feed), drawn at the moment a message is scheduled; the per-channel FIFO clamp is `max(sampled, last arrival on the channel)`.
- D-082 The rejection-sampling unbiasedness test uses a range of size 3 * 2^62: the modulo bias on a range of 3 values is about 2^-64 and cannot be measured, whereas on this range the lowest third would have probability 1/2 instead of 1/3 without rejection.
- D-083 `seconds_to_ns` clamps a run-time draw to 4e18 ns (and NaN to that value), and config validation bounds `duration_s` to 1e9 s and every configured duration (latency, jitter, period) to 1e18 ns, so `now + draw` stays below 2^63 for any valid run; before, a tiny `lambda` or a huge `order_lifetime_mean_s` could make the double-to-int64 cast undefined.
- D-084 The config `seed` accepts any unsigned 64-bit value, like `--seed`.
- D-085 The informed trader keeps one wakeup chain: `on_start` and every `on_wakeup` draw exactly one exponential from `ctx.rng()` and schedule the next wakeup before looking at the market, so its wakeup times never depend on prices. Its only look at the world is the last BBO it received and `Fundamental::value()`, read at wakeup. It uses plain `schedule_wakeup` (no `TimerQueue`) because it has a single kind of timer.
- D-086 The informed trader compares in ticks as doubles: buy if `V - ask >= theta` (needs an ask in the local BBO), else sell if `bid - V >= theta` (needs a bid). A one-sided BBO evaluates only the side it has; if both conditions hold (impossible with a non-crossed book and theta >= 0) the buy wins. Orders are market IOC, `STP::CancelTaking`, own `client_order_id` counter from 1; nothing rests, so `on_private` only counts events.
- D-087 The scripted `FakeCtx` moved unchanged from `sim_noise_trader_test.cpp` to `tests/support/fake_context.hpp` so the informed-trader tests share it. `Integration.FiveMinutesOfTheDefaultNoiseFlow` now expects 11 agents (10 noise traders and the informed trader); the default config's event hash changes because it now has an informed trader, while a config with no `informed` section keeps the noise-only hash ac6dbb79a513fa50.
- D-088 New optional config key `noise_traders.reference_price` (`"floor"` or `"symmetric"`, anything else is an error naming the field; `to_json` always writes it). `floor` is the rule of SPEC 5.6: buy at `floor(mid) - d`, sell at `floor(mid) + d`. `symmetric`: buy at `ceil(mid) - d`, sell at `floor(mid) + d`; it differs only when the local BBO is two-sided with an odd spread, needs no random draw, and leaves the fallbacks (last trade, initial price) unchanged.
- D-089 `configs/default.json` sets `"reference_price": "symmetric"`, the one deliberate departure from the SPEC 5.8 values. With the spec's floor rule, an odd spread lets sell limits (ref + d) improve the best ask by a tick while buy limits (ref - d) can only join the best bid; over 12 seeds of a noise-only one-hour run the final mid minus the start price was -91 to -117 ticks with floor, +97 to +121 with the mid rounded up, and -9 to +15 with the symmetric rule, a rounding artefact larger than the fundamental's one-hour standard deviation (60 ticks).
- D-090 The key is optional and defaults to `floor`, so the JSON of SPEC 5.8 keeps meaning exactly what the spec says and `simtest::default_json()` stays the spec text; the noise-only one-hour hash ac6dbb79a513fa50 is unchanged.

## Avellaneda-Stoikov market maker (Phase 6; SPEC 1, 5.6 item 3, 9 item 6)
- D-091 The quotes come from one pure function `compute_quotes(params, local BBO, q, now, end)`, tested on its own. `tau = max(0, end - now)` in seconds. Prices stay doubles until the range check, so an extreme `r` never overflows the integer conversion. "Ensure bid < ask" lowers the bid to `ask - 1`; with `delta > 0` and the two clamps it is reachable only when `r +- delta/2` rounds onto the same integer.
- D-092 Reprice by `Modify` only when a full extra quote cannot break the limit (bid: `q + quote_size <= q_max`; ask: `-q + quote_size <= q_max`), otherwise `Cancel`, and the `NewOrder` comes from the ordinary requote once the cancel's reply has arrived. Reason: a `Modify` resets the remaining quantity, so one that arrives after unseen fills refills the order; always modifying allows `q_max + 2 * quote_size - 2`, this rule bounds `|q|` by `q_max + quote_size - 1` (argument in `as_market_maker.cpp`). The stress test reaches exactly 14 with `q_max` 10 and `quote_size` 5.
- D-093 Per side the agent keeps at most one pending request and never sends another until its reply arrives: `Ack` / `Reject(New)` matched by `client_order_id`, `Modified` / `Reject(Modify)` / `Cancelled(User)` / `Reject(Cancel)` matched by kind and order id. Trades never clear a pending request. The requote runs after every BBO, every `requote_interval` wakeup and every private message; after a `PostOnlyWouldCross` reject it acts at once on the BBO it has, which may still be the stale one (then the same request is sent again and rejected again until the fresh BBO arrives); no extra back-off state was added.
- D-094 Messages that fit no state count in `anomalies()` and never crash or corrupt state: a reply with no matching pending request is ignored; a trade for an unknown order still moves the inventory (it happened); a `Cancelled` other than the reply to a pending cancel removes the order; `Reject(UnknownOrder)` for an order still believed resting (impossible: its fills arrive first) drops it; `Modified` for an order believed gone takes the exchange's word. In a correct run the counter is 0, and the tests assert that.
- D-095 The market maker draws no random numbers and keeps one wakeup chain (`on_start` schedules `requote_interval`, each `on_wakeup` schedules the next one, then requotes), with plain `schedule_wakeup` like the informed trader (D-085). It is created last, with streams (MarketMaker, 0); `Simulator::market_maker_index()` returns its index. `lobsim_run` prints its true inventory, maximum `|q|` and fills from an observer over engine `Trade` events, and its requests, rejects and anomalies from the agent's own counters.
- D-096 The stress test's aggressor sends every order with `STP::CancelResting`: with `CancelTaking` its market orders stopped at its own resting limits and the market maker was hit 9 times in 30 s; now a market order removes the aggressor's own orders in its way and reaches the quotes (about 4,800 market-maker fills per 60 s seed).
- D-097 `Integration.FiveMinutesOfTheDefaultNoiseFlow` now expects 12 agents (the market maker exists). No test pins a golden simulation hash (it depends on the platform's maths library). Instead `MarketMakerSim` checks that a run with the `mm` section differs from one without it, and `Determinism.AddingTheMarketMaker...` / `AddingTheInformedTrader...` (with the configured latencies and under 300 ms jitter) check that adding either agent leaves every noise trader's own `NewOrder` decisions unchanged.

## Metrics, output files, replay and plots (Phase 7; SPEC 5.7, 6, 9 item 7)
- D-100 Metrics come from one observer (`MetricsObserver`) that sees engine events and the true top of book with zero latency; it never schedules, sends or draws, and a test checks that attaching it leaves the event hash and `orders.log` unchanged. `lobsim_run` no longer has its own market-maker probe; it prints only what the agent alone knows (its requests, rejects, anomalies and believed inventory).
- D-101 Every metric is a function of "the state after all events with timestamp <= t" or, for the instant `warmup`, "the state after all events with timestamp < warmup" (so the window `[warmup, T]` is closed at its start and `pnl_after_warmup = pnl(T) - pnl(warmup)` counts exactly the fills with `t >= warmup`). Events at exactly T are never processed (kernel rule), so the final state is the state at T.
- D-102 Market-maker accounting: `cash` is `int64` ticks x lots (a buy subtracts `price * qty`, a sell adds it), `inventory` in lots, both from t = 0; fees are `double`, `qty * maker_fee_ticks` if the market maker was the maker else `qty * taker_fee_ticks` (a negative fee is a rebate); `pnl(t) = cash + inventory * mid(t) - fees` with `mid(t)` the last defined mid at or before `t`, and 0 for the mark if no mid has ever existed.
- D-103 The market maker's resting orders are tracked from engine events (Ack of its own `NewOrder`, Trade, Cancelled, Modified), not read from the book; "quoting" means at least one resting bid and one resting ask, and the quoted spread is its lowest ask minus its highest bid.
- D-104 Window statistics integrate state over `[max(warmup, previous event time), min(now, T))` at every state-changing hook (request, fundamental step, sample, end): time-weighted spread distribution and quoting time are exact to the nanosecond, with no sampling.
- D-105 Spread median, p90 and p99 are time-weighted quantiles on integer tick values: the smallest spread whose cumulative time reaches `p * total`. The histogram has one bin per spread 1..40 ticks (fraction of two-sided time) and one overflow bin; a spread of 0 cannot exist because the book is never crossed.
- D-106 Markouts: fill at `t`, horizon `h` -> mid in force at `t + h` (state after all events with timestamp <= `t + h`, resolved lazily when the next event with a later timestamp arrives, or at the end). A sample is skipped and counted if the mid is undefined at that instant or `t + h > T` (`t + h == T` is valid); `n + skipped` equals the number of window fills. Statistics: mean, sample sd (n - 1), 95% interval `mean +- 1.96 sd / sqrt(n)` (null for n < 2), and the quantity-weighted mean. Fills before the warm-up get markouts in `mm_fills.csv` but are not in the statistics.
- D-107 Returns: the mid is sampled at `k * sample_interval` for every k with `warmup <= k * interval <= T` (the sample at exactly T is taken at the end); a sample sees the state after every event ordered before the kernel's Sample event (time, then seq), and `bbo.csv` also has the t = 0 row. A log return exists only between two consecutive present samples; excess kurtosis is `m4 / m2^2 - 3` with central moments divided by n; autocorrelation is `sum((x_t - m)(x_{t+k} - m)) / sum((x_t - m)^2)` over pairs where both terms exist, with `m` the mean of all present values (nothing is interpolated). The returns are of a half-tick-quantised mid, so they are mostly zero or one of a few tick-sized values.
- D-108 Counts: requests by type are requests arriving at the exchange (they sum to `Exchange::requests()`); "orders sent" per role counts `NewOrder` sends by agents (some may still be in flight at T); roles follow creation order (noise traders, informed trader, market maker), and agents added by tests are `Role::Other` and not reported.
- D-109 Files: `trades.csv`, `bbo.csv` and `mm_fills.csv` write integers as integers, sides as `buy`/`sell`, roles as `maker`/`taker`, `mid` and markouts with `%.1f` (they are multiples of 0.5), fundamental and PnL with `%.6f`, an undefined value as an empty field; `summary.json` is written with `nlohmann::ordered_json` (key order fixed in the code, config echoed from `to_json`), doubles rounded through `%.6f` and null when undefined (exception: the return `mean` and `sd` use `%.6e`, six significant digits, because they are around 1e-6), two-space indent and a trailing newline. No wall-clock time, host name or path is written; elapsed time goes to stdout only.
- D-110 `replay_log` (in the `sim` library) is the one replay implementation: `lobsim_replay`, `tests/replay.cpp` and the command-line test all use it. A bad header or request line throws `ReplayError` carrying the 1-based line number; the tool prints it and exits 1. The command-line ctest `cli_run_then_replay` runs `lobsim_run --duration-s 120`, replays the log, compares the printed hash with `summary.json` and checks that a corrupted log is refused.
- D-111 `tools/plot.py` needs only pandas, matplotlib and numpy (a pandas dependency), draws the warm-up as a grey band, takes the spread histogram and the return ACF from the sampled `bbo.csv` rows (so its numbers are the sampled ones, not the time-weighted ones of `summary.json`), and exits 1 with a message if `bbo.csv` or `summary.json` is missing.
- D-112 `mid_before` of a market-maker fill is the mid in force just before the request that caused the trade was applied (captured in `on_request`; undefined when the book is one-sided at that moment, however recently a mid existed, and such a fill is left out of the decomposition, as the markout treats an undefined mid at `t + h`). It is the `mid_before` column of `mm_fills.csv`, placed before the `markout_*` columns.
- D-113 `spread_capture = mid_before - p` for a buy and `p - mid_before` for a sell (ticks per lot): what the fill earned against the pre-trade mid; the `spread_capture` block of `summary.json` covers window fills with a defined `mid_before` (n, mean, sd, 95% interval, quantity-weighted mean).
- D-114 `mid_move(h) = m(t+h) - mid_before` for a buy and `mid_before - m(t+h)` for a sell, with `m(t+h)` exactly as in the markout; negative means the price moved against the market maker (the adverse-selection number). It is computed as `markout(h) - spread_capture`, so `markout = spread_capture + mid_move` holds on every fill where all three are defined.
- D-115 Each markout's `decomposition` object is computed over window fills whose markout and `mid_before` are both defined (`n` can be smaller than the markout's `n`); on that subset `spread_capture_mean + mid_move_mean = markout_mean` up to rounding. A fill with no `mid_before` keeps its markout but is left out of the decomposition.

## Fuzzing and CI (upgrade 1; FUZZING.md)
- D-116 The spec's names match the code's: `OrderBook`, `ReferenceBook`, `NewOrder`, `Cancel`, `Modify`, `validate()`, `LOBSIM_SANITIZE`. `Request` is `std::variant<NewOrder, Cancel, Modify>`, and the books' `submit` / `cancel` / `modify` are fed through `lob::apply` (D-012). The driver lives in `lob::fuzz` (`fuzz/diff_driver.{hpp,cpp}`), with `kFuzzMaxPrice` = 1000.
- D-117 `decode()` resolves Cancel/Modify targets with a private `ReferenceBook`, not an `OrderBook`: both books give the same ids up to the first mismatch, a crash file must still decode when the fast book faults, and the injected-bug macros of a later phase never touch the reference. `run_diff()` does not call `decode()`; it decodes record by record with `decode_record` and takes `known_ids` from the live Acks of the fast book (SPEC 3.1), so the byte-to-request mapping has one source.
- D-118 Beyond the event buffers and `validate()` (SPEC 3.2), `run_diff` compares `depth(Buy/Sell, SIZE_MAX)` and `resting_orders()` after every request, and `order(target)` of the two books after every Cancel/Modify, so a state difference shows on the request that causes it rather than at a later event.
- D-119 Every `apply()` and `validate()` call in `run_diff` is wrapped in `try/catch (const std::exception&)`: in a non-NDEBUG build the books call `validate()` themselves and throw `std::logic_error` from inside `submit/cancel/modify`, and an exception leaving `run_diff` would reach `std::terminate` before the report is printed. The report names the book and `e.what()`, then `std::abort()`. `decode()` ignores such a throw from the reference book so a crash file still decodes.
- D-120 The regression test (`tests/fuzz_regressions.cpp`, `fuzz_regression_tests`) lists `fuzz/regressions/diff/` then `fuzz/corpus/diff/` when it runs (non-recursive, regular files, names starting with '.' skipped so `.gitkeep` can hold an empty directory, sorted by name) and is registered with a plain `add_test(NAME fuzz_regressions_diff ...)`. `gtest_discover_tests` is not used: its list is cached at build time and would silently skip a file added later. Parameter names are the sanitized file name with a `regressions_` / `corpus_` prefix, made unique with `_2`, `_3`. ## Book-builder operations (upgrade 2, R1)
- D-151 Both books gain four mutating or previewing operations and one query, with the same API and semantics: `insert_passive`, `reduce`, `remove`, `preview_match`, `level_orders`. They exist so that a feed replayer can place and take away orders without matching, because the exchange has already matched. `submit`, `cancel` and `modify` are unchanged. Types, in `lob/types.hpp`: `enum class Status { Ok, WouldCross, UnknownOrder, Oversized, InvalidQty, InvalidPrice }` (with `to_string`), `Result<T>{Status status; T value; ok()}` (value-initialised, so `0` for an id on failure) and `Fill{maker_id, price, qty}`. All have `operator==`, because the differential fuzzer compares them exactly. None of the operations emits events: a replayer knows what it asked for.
- D-152 `insert_passive` takes its OrderId from the same counter `submit` uses (`next_order_id_`), exactly as an Acked `NewOrder` does, so ids stay dense and the id-indexed vector of the fast book stays small; an exchange order id is never used as an engine id. Validation order is that of `NewOrder` (SPEC 3.2, first failing check wins: quantity, then price range; there is no flags check here) followed by `WouldCross` (a buy at a price >= the best ask, a sell at a price <= the best bid, as for post-only). On any failure nothing changes and no id is consumed. The order is a plain GTC limit: `stp = CancelTaking`, `post_only = false`; `owner` defaults to 0 (no simulated agent has owner 0). It lands at the tail of its level (`ReferenceBook`: the next `priority_seq`).
- D-153 `reduce(id, qty)`: `qty <= 0` is `InvalidQty` (checked before the id lookup); an id that is not resting is `UnknownOrder`; `qty == remaining` removes the order (`Ok`); `qty > remaining` also removes it and returns `Oversized` (the replayer counts such messages; the order cannot be left behind with a quantity the feed says is gone); `qty < remaining` reduces in place and keeps the queue position and the level's total. `remove(id)` is `Ok` or `UnknownOrder`. In a non-`NDEBUG` build `insert_passive`, `reduce` and `remove` call `validate()` at the end, like `submit`, `cancel` and `modify`.
- D-154 `preview_match(taker_side, limit, qty)` is a const walk of the opposite side, best price first and first in first out inside a level. It stops when the next level is worse than `limit` (a buy: level price > limit; a sell: level price < limit) or `qty` is filled. It returns one `Fill` per touched order, with the quantity taken from it (the last may be partial) and the level's price. It does not look at owners (no self-trade prevention) and changes nothing. `qty <= 0` gives an empty list. The `limit` is not range-checked: a limit outside `[1, max_price]` simply admits all or no levels.
- D-155 `level_orders(side, price)` returns the resting `OrderView`s at one price on one side in priority order, empty if there is no such level. It is on both books, and fuzzed against the reference, because the replayer needs it to resynchronise a level against the feed and to attribute a seed order to its place in the queue, and because it is the only query that exposes the queue order of a level: depth sums quantities, and `order(id)` shows one order. In the reference book it is a filter by side and price sorted by `priority_seq`; in the fast book it is a walk of the level's list.
- D-156 The fuzz target `fuzz_diff_builder` (`run_diff_builder`, corpus `fuzz/corpus/diff_builder/`, regressions `fuzz/regressions/diff_builder/`) uses the 8-byte records of `fuzz_diff` with `kind = b0 % 7`: 0 to 2 decode through the same code as `fuzz_diff` (`decode_fields`; the 19 seeds of `fuzz/corpus/diff` decode to the same text as before), 3 is `insert_passive` (side bit 0 of `b2`, price, qty and owner by the shared rules), 4 is `reduce`, 5 is `remove` (the target by the shared rule), 6 is `preview_match` (the price is the limit). `known_ids` holds every Ack and every successful `insert_passive` id, in order. After each operation the return values (status, new id, fill list) and the event buffers must be equal; then the post-request checks of `run_diff` run, plus `level_orders` of both books for the levels the operation touched, found in the reference book before the operation (a New: its side and price; an insert: its side and price; reduce, remove, cancel: the target's level; a modify: the target's level and the new price on its side; a preview: the best level of the side it walks). The C++ names are `BuilderOp`, `decode_builder_record`, `decode_builder` and `op_to_string` (not an overload of `to_string`, which would be ambiguous for `NewOrder`, `Cancel` and `Modify`, since each converts to both variants). `lobsim_fuzz_decode --builder <file>` decodes such an input. `make_seeds.py` now writes both corpora by default and has `--out-builder` and `--check-builder`; `fuzz_seeds_up_to_date` checks both. The 11 named seeds (`insert_passive_basic`, `insert_passive_would_cross`, `insert_passive_at_tail`, `reduce_partial`, `reduce_exact`, `reduce_oversized`, `reduce_unknown`, `remove_basic`, `preview_across_levels`, `builder_mixed`, `mixed_builder_stream_64`; the stream is SplitMix64 seed 2) are required by `FuzzCorpus.CommittedSeedsAreFound`; the suite `DiffBuilder` (ctest `fuzz_regressions_diff_builder`) runs every file of the two folders.

- D-160 Time is parsed as text: integer seconds (digits only, `from_chars` into `uint64_t`, so overflow is detected) times 10^9 plus the fraction padded on the right to 9 digits. The check for types 1 to 5 is unchanged (size > 0; price > 0 for types 1 to 4; a type 5 hidden execution may carry price 0).
- D-162 One trailing `'\r'` is removed before a line is split (a file with CRLF line ends), and `Parsed::cr_stripped` records it; a second `'\r'` stays in the last field and the line is rejected as non-numeric. Fields are integers only: an empty field, a leading `+`, a space or a decimal point is rejected; a leading `-` is accepted where the value may be negative.
- D-163 Orderbook rows: exactly `4 * L` fields, per level the ask price, ask size, bid price, bid size. Size 0 is an empty level whatever its price. The exact placeholder LOBSTER writes for an empty level could not be verified (the sample README was not available); the seeds use `9999999999` / `-9999999999` with size 0 because it is the commonly reported convention, and the parser does not depend on it. ## LOBSTER replayer (upgrade 2, R3)
- D-168 The replayer is in the `replay` library (`include/replay/replayer.hpp`; `src/replay/replayer.cpp` replays, `src/replay/replayer_match.cpp` runs the matching check, `src/replay/replayer_json.cpp` and `src/replay/replayer_text.cpp` write the reports; several files for the reason of D-158 and D-186). `Replayer(levels, ReplayOptions{mode, compare_depth, trust_depth, max_lookahead})` and `run(messages, orderbook)` stream both files line by line through a small reader that keeps a deque of parsed lines ahead of the current one, for the burst lookahead of the matching check; more than `max_lookahead` (100,000) buffered lines is an `InputError`, never unbounded buffering. `replay_files(messages_path, orderbook_path, options)` opens the files and takes `L` from the orderbook file name. The book is `lob::OrderBook` with `max_price = 2'000'000'000`, prices in LOBSTER units. The replayer keeps the depth to which the previous row was exact before any correction, for the trust rule of the matching check.
- D-169 Lines are numbered from 1, the same number in both files: line k of the orderbook file is the book after line k of the message file (the spec's "row 0" is line 1). Every line is compared with the oracle, line 1 included (after seeding it is exact unless the book refused part of the seed); `rows_compared` is the denominator of every exact-row rate.
- D-170 Message handling beyond the spec's table. A known id whose Direction is not the order's side (`direction_mismatch`, checked for types 2, 3 and 4, not only 4) or whose price is not the order's price (`price_mismatch`) is skipped and the book is left unchanged: the id then names an order that disagrees with the message. Direction is checked first, and a message is counted once. A type 3 whose size is not the remaining is still deleted and counted `delete_size_mismatch` (spec 4.1). `oversized_reduce` is counted for type 2 as well as type 4 (`reduce` removes the order either way, D-153). A type 1 above `max_price` is `submit_bad_price`. Seed attribution of a type 3 reduces the synthetic order by the message size. Every message lands in exactly one outcome counter (`parse_rejected`, `consumed_by_seed`, `submitted`, `dup_id`, `submit_would_cross`, `submit_bad_price`, `cancelled`, `deleted`, `executed`, `direction_mismatch`, `price_mismatch`, `seed_attributed`, `unknown_id`, `hidden_exec`, `cross_trade`, `halt`); the fixture test checks that these sum to `messages`. `seed_orders` and `seed_rejected` count the synthetic orders placed from line 1.
- D-171 Bad input. A message line that does not parse is counted `parse_rejected` and skipped; its orderbook line is still compared. An orderbook line that does not parse (after line 1) is counted `oracle_rejected` and not compared, the trust depth falls to 0, and strict mode stops there (exit 2). Fatal (`InputError`, exit 1): a file that cannot be read, an orderbook file name without `_orderbook_<L>.csv`, a message file name whose `L` differs, a line 1 whose column count is not `4 L` or that does not parse (the opening book is seeded from it), and files with different line counts (found when the first one ends).
- D-172 The resync window of a side is every price at least as good as the oracle's L-th level, or the whole side when the oracle shows fewer than L levels. The spec's "from the best price to its L-th price" read literally would leave a stale level that is better than the oracle's best untouched forever; the touch is always published, so such a level is removed (at its rank, 1 when it is our best). The exporter's `--filter-window` uses the same window. Removals on both sides come first, then the size corrections, so a synthetic insert never meets a level that is about to go. `corrected_by_level[d]` counts levels fixed (one per row and level); a synthetic insert the book refuses (only possible with a crossed oracle row) is counted `resync.failed` too. Removed levels of rank above L are counted `removed_beyond_level_l`. A malformed oracle row (D-164) is never used to correct (`resync.skipped_malformed`). Resync runs only on rows not exact at depth L; a row exact at L leaves nothing to correct.
- D-173 `crossed_state` is counted as the spec says, but with `lob::OrderBook` it is always 0: `insert_passive` refuses a crossing order (counted `submit_would_cross`) and `validate()` rejects a crossed book. `submit_would_cross` is where an uncorrected drift shows up instead.
- D-174 Outputs. `summary.json`: mode, levels, compare and trust depth, `completed`, `strict_failure_line`, `lines`, `rows_compared`, `counters` (all of the above, plus `messages`, `type_1`..`type_7`, `time_truncated`, `oracle_malformed`, `oracle_rejected`, `crossed_state`), `exact_rows` (per depth: `exact`, `rows` and a `percent` string), `divergent_rows`, `resync` (`rows`, `corrected_by_level`, `removed_by_rank`, `removed_beyond_level_l`, `failed`, `skipped_malformed`), then `wall_ns` and `messages_per_second`; everything but the last two is deterministic, and that part is what the fixture test compares. Percentages are integer arithmetic, cut (not rounded) to two decimals. `divergences.csv` (`line,depth,side,ours_price,ours_size,oracle_price,oracle_size`): the first 1,000 rows not exact at depth L, one line per side that differs at the first differing depth; a level the book does not have is written with an empty price and size 0, the oracle's level as given. On stdout: the one-screen summary with the interpretation rule, and for a strict failure the line, both books side by side and the last 20 message lines.
- D-175 `lobsim_lobster` exit codes: 0 done, 1 bad arguments or input that cannot be replayed, 2 strict failure. `--compare-depth` must be in 1..L; `--trust-depth` must be at least 1 (it has no upper bound here: the matching check reads it).

## Matching agreement (upgrade 2, R6)
- D-180 Bursts. The replayer starts a burst at a parsed type-4 message that is not already part of one, and collects the rest through the reader's capped lookahead: the following lines while each parses, is type 4, and has the same time and Direction (a line that does not parse ends the burst, as any other type does). The check runs before the burst's first message is applied; the messages are then applied one at a time as before, with an oracle comparison after each. Line 1 is consumed by the seed and never part of a burst; if executions continue it, the burst starts at line 2. Strict mode may stop inside a burst. The 100,000-line lookahead cap (D-168) also covers the 5 lines read after a burst for an example.
- D-181 The two sides of the comparison. Data: each message, in order, as the replay will apply it, without changing the book. A known id whose order still has quantity left after what earlier messages of the burst take is `(external id, message price, size)`; a message that will be skipped (Direction or price disagreeing with the order, D-170) takes nothing. Otherwise the message goes through seed attribution as in 4.3, on what the earlier messages left of each synthetic order, and is `SYN@price`; if no synthetic order fits, the burst is `excluded_unknown`. Prediction: `preview_match(opposite of Direction, worst price of the burst, sum of sizes)`, with makers mapped back to external ids; a synthetic maker (or one without an external id) is `SYN@price`. Fills are written `<id> <size> @ <price>` or `SYN@<price> <size> @ <price>`.
- D-182 Classes, in this order: `excluded_unknown` (the same at every trust depth); `excluded_untrusted` when the previous row was not exact before correction down to T or T < distinct prices + 1; otherwise the comparison. Equal fills with no synthetic fill on either side are `exact`; equal when a synthetic fill matches a synthetic fill at the same price and size are `exact_via_synthetic` (a synthetic and a real id never match). Otherwise the first differing fill decides: a different price is `price_skip`, the same price with a different order `queue_order`, the same order and price with a different size `size_split`; if every fill both lists have is equal, `length`. `price_skip` is split into `price_skip_better` (the prediction is at a better price for the taker: lower for a buyer, higher for a seller; this is the spec's definition) and `price_skip_worse` (the data filled at a price where the book had less: lobsim's walk went on to a worse price). Both count as `price_skip`, so every burst has exactly one class. `first_difference` is 1-based; for `length` it is the shorter list's length + 1.
- D-183 Trust depths and output. The counts are computed in one pass for each of the distinct depths among 1, 3, L and `--trust-depth` (default 3, the headline), in ascending order; a depth above L can never be trusted. Agreement = (`exact` + `exact_via_synthetic`) / (bursts − both exclusions), always printed as numerator / denominator with every exclusion count. `summary.json` has a `matching` block: `bursts`, `burst_messages`, `headline_trust_depth`, `by_trust_depth` (per depth: the eight class counts, the two price-skip counts, `numerator`, `denominator`, `percent`) and `examples`: the first 3 bursts of each mismatch class at the headline depth, each with its first line, `first_difference`, `price_skip` (better or worse, price-skip examples only), the burst's lines, both fill lists, and up to 5 lines before and after. Strings are JSON-escaped (example lines come from the input). The check runs in every mode. Its code is in `src/replay/replayer_match.cpp`.
- D-184 Tests. New fixture `tests/fixtures/lobster/matching` (27 lines, every row exact) with one burst per class; the expected summary, including the examples, was derived by hand. The `MatchingClass.*` tests replay it up to the end of one burst and check that exactly the expected counters went up against the previous burst's end; `excluded_untrusted` is also checked on the resync fixture, where the previous row was not exact. The existing fixtures' matching blocks were derived by hand too. `basic_types` has a `queue_order` at line 11: the hand-written data executes order 22 while the opening seed is ahead of it in the queue, so it stays as written, as an example of that class. `MatchingBurst.TheLookaheadIsCapped` checks the cap. The unfiltered closed loop now also requires, at trust depth 3, agreement of every scored burst, at least one scored burst, and zero `queue_order`, `price_skip`, `size_split`, `length` and `excluded_unknown`. Measured: the 60 s run of the test has 370 bursts, 370/370 at T = 3 and T = 10 (369/369 filtered at T = 10); 600 s runs of the default config, unfiltered, strict at depth 10: seed 7 has 4,994/4,994 at T = 3 (2 bursts of 3 or more prices excluded), seed 11 4,645/4,645 (4,642 exact, 3 via a synthetic order, 5 excluded).

With the matching check's reports the D-158 linker failure came back on the macOS fuzz build (`ld: invalid r_symbolnum=1 in '../libreplay.a(replayer_report.cpp.o)'`, then on `replayer_json.cpp.o` after a split): Apple `ld` reads every member of the archive, so all four fuzz targets failed to link although none uses the replayer. Messages before the window update the mirror book but are not written and are counted separately (`messages_before_window`), not as "filtered".
- D-207 Hidden executions: a Poisson stream drawn with the project's `Xoshiro256StarStar` (stream seeded by `--seed`). Gap = `exponential(rate)` truncated to whole nanoseconds, the only floating point and never written to a file. Per event, size (1-100) and direction are drawn first, then the price is `uniform_int(best bid, best ask)` of the true book; if the book is not two-sided the draw is skipped and counted (0 in both fake days). Ids are 2^40 + k; the export fails if a simulator order id ever reaches 2^40. Injected messages at the same instant as real ones go after them (the pending stream is flushed only up to `request time - 1 ns` before a request); a hidden execution and the halt at the same instant: hidden first. Rows of injected messages repeat the last written row (the current true book if none was written yet).
- D-208 Empty levels are `0,0` (price, size) in `--lobster-like` rows only; the default export keeps +-9999999999. The halt is type 7, price -1, size 0, id 0, direction 1 (our stand-in encoding). Output into a directory whose normalized path ends in `data/lobster` is refused with exit 1 before anything is created. `README_SYNTHETIC.txt` and `<ticker>_injected.json` are written next to the files; the json is what tests compare with the replay's `hidden_exec` and `halt` counters.
- D-209 `SYNTHA`: `configs/default.json`, run seed 20120621, hidden-stream seed 101. `SYNTHB`: `configs/synthb.json` = default with `informed.lambda` 2.0 -> 8.0 (x4) and `noise_traders.lambda` 5.0 -> 10.0 (x2, per trader, 10 traders), run seed 20120622, hidden-stream seed 202. - D-211 Bug found by the dress rehearsal (matching check): two aggressive orders at the same nanosecond on the same side form one burst (spec 7.1), and when the first stops inside a resting order the next one goes on from there, so the data names that order twice in a row ("6 4", "6 1") while `preview_match` for the burst's total fills it once ("6 5"): a `size_split` that is not a disagreement. - D-214 `tools/lobster_audit.py` (Python 3, standard library only; synthetic exports only, real files have no audit): `--audit`, `--messages`, `--orderbook`, `--summary` (a completed resync run), optional `--json`. It (1) replays the files again by the rules of the replayer (seeding, the message table of D-170, seed attribution, resync with removals and tail trims, bursts with the merges of D-205 and D-211) and requires every counter, exact-row count, correction and removal count and burst class at every trust depth of `summary.json` to be equal; (2) rebuilds the true book from the audit and requires it to equal every orderbook row, and every burst's executions to be the true book's own price-time walk for the burst (consecutive fills of one order merged); (3) attributes every corrected and removed level (all depths), `delete_size_mismatch`, `oversized_reduce`, `unknown_id`, every burst whose comparison disagrees (scored or not) and every `excluded_unknown` burst. A level is explained when every order-level difference between the replayed and the true book there has a root and there is at least one: a stale known order whose removal was a filtered message; a known order with less than the truth because a trim or level removal that was itself explained cut it; a known order with more because a reduction of it was filtered; synthetic orders holding more than the true orders the replay does not know, covered by filtered deletes of such orders at that price since the oldest synthetic order there was placed; a true order the replay does not know because its submission was filtered, it rested below level L when the window opened, or an explained correction cut it (orders inside line 1's seed, including message 1's, are covered by the seed). An order item is explained by an explained cut, a filtered reduction, a filtered submission, the opening depth, or, for an order inside the seed, a seed order drawn down by cut orders or explained trims. It prints the counts per cause, which add up to the summary's totals, and every unexplained item; exit 0 when everything is reproduced and explained, 1 otherwise, 2 for input it cannot read. It also counts the references to orders below level L at the window start made before their price was ever inside the published window, which the CI test compares with `unknown_id`. Self-test `lobster_audit_self_test` (`tests/lobster_audit_test.py`, hand-written files): a filtered delete removed at rank 1 is explained (exit 0); the same book with every message written passes; a message file with one delete naming the wrong order gives an unexplained `unknown_id` and level-1 correction (exit 1); a summary with `unknown_id` raised by one fails the reproduction (exit 1). On the full days it takes about 3 minutes (SYNTHA) and 6 (SYNTHB).
